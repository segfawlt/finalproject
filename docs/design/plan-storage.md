# Plan Storage

This document describes how plans, iterations, snapshots, and execution state are persisted.

---

## Plan JSON Structure (`PlanData`)

The `plans` table stores a single JSONB column `plan_data` that contains the full plan state:

```
PlanData {
  llmResponse?: { summary, reasoning }
  desiredState?: DesiredState
  executionSteps?: PlanStep[]
  symbolTable?: SymbolTable
  assumptions?: Assumption[]
  snapshots?: { before?: string, after?: string }
  results?: { created, modified, deleted }
}
```

### Field descriptions

| Field            | Description                                                                       | Lifecycle                                                                                              |
| ---------------- | --------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| `llmResponse`    | Final summary and reasoning from the planning LLM                                 | Set when the planning loop terminates                                                                  |
| `desiredState`   | The full DesiredState (active items + tombstones) produced by the planning loop   | Set at the end of each planning turn; overwritten on revision                                          |
| `executionSteps` | Steps generated by the diff engine (Phase 1–3)                                    | Generated on demand at execution time from DesiredState; the completed steps are written back into `planData` after execution for audit |
| `symbolTable`    | Maps `$ch_0`, `$role_0`, etc. to step indices and resolved Discord IDs            | Built by diff engine; symbols resolve during execution as creates succeed; persisted into `planData` after execution                    |
| `assumptions`    | Pre-execution checks (e.g., "parent category exists")                             | Generated from tool `getAssumptions()`; evaluated fresh against current Discord state before execution |
| `snapshots`      | IDs referencing rows in the `snapshots` table captured before and after execution | Set during execution; enables rollback                                                                 |
| `results`        | Simple summary of what was created/modified/deleted (`{created, modified, deleted}`) | **Defined in the type but not currently populated** — the execute route never writes `results`. See implementation gaps. |

## Iterations (`plan_iterations`)

Planning is iterative. Each turn of the planning loop produces a new version of the DesiredState, saved to the `plan_iterations` table:

```
plan_iterations {
  id: uuid
  conversation_id: uuid → conversations
  version: integer (1, 2, 3, ...)
  type: "llm_generated" | "manual_edit" | "revert"
  desired_state: jsonb (DesiredState snapshot)
  created_at: timestamp
}
```

- **Version** is monotonically increasing per conversation.
- **Type** records whether the iteration came from the LLM, a manual Studio edit, or a revert.
- On server restart, the latest iteration for a conversation is loaded back into memory to resume planning.

### Why separate from `planData`?

Originally, all iteration history was stored inside the `planData` JSONB monolith. This made the blob grow unbounded and complicated reverting to prior states. Extracting iterations to a dedicated table:

- Keeps `planData` bounded (current state only)
- Makes reversion O(1): load a prior `desired_state` row, overwrite current state
- Enables iteration history in the Studio UI

## Snapshots (`snapshots`)

The `snapshots` table stores full server-state captures used for rollback and audit:

```
snapshots {
  id: uuid
  type: "execution_before" | "execution_after" | "role_deletion" | "plan_state"
        // only execution_before / execution_after are written today;
        // role_deletion and plan_state are reserved (in the type, never inserted)
  guild_id: text → guilds
  plan_id: uuid? → plans
  data: jsonb (full ServerState at point in time)
  created_at: timestamp
  expires_at: timestamp? (for cleanup)
  metadata: jsonb?
}
```

### Snapshot lifecycle

1. **Before execution**: capture current Discord state → `execution_before`
2. **After execution**: capture post-execution state → `execution_after`
3. **On rollback**: use `execution_before` data to reconstruct what existed
4. **Expiration**: snapshots older than their `expires_at` are deleted by the cleanup job (`snapshot-cleanup.ts`)

### Rollback mechanics

When execution fails mid-plan (or an after-the-fact rollback is requested),
`rollbackFull()` (`execution-engine.ts`) performs a **diff-based** rollback, not
a per-step inversion:

1. Read fresh current Discord state (`buildCurrentStateFromDiscord`)
2. Fork the `execution_before` snapshot into a DesiredState (`fork(beforeSnapshot)`)
3. Run the diff engine `diffEngine(currentState, desiredBefore)` to compute the reverse steps
4. Execute those steps as a normal plan via `executePlan`
5. This is **best-effort structural rollback** — messages and member assignments cannot always be restored

Because rollback recomputes the delta from live state, it does not depend on
walking `completedSteps`, and external changes made since execution are handled
uniformly.

## Plan Status State Machine

A plan row is created when the user approves a conversation, so it starts at
`draft`. Validation is not a separate user step: it runs at the start of
execution, which is the transition that flips `draft → validated`.

```
draft ──► validated ──► executing ──► completed
                            │
                            ▼
                          failed ──► rolled_back
```

The `PlanStatus` type (`packages/shared/src/types.ts`) is:
`"draft" | "validated" | "approved" | "executing" | "completed" | "failed" | "rolled_back"`.

| Status        | Meaning                                                                     |
| ------------- | --------------------------------------------------------------------------- |
| `draft`       | Plan created from an approved conversation; not yet executed                |
| `validated`   | Stage 1 deterministic validation passed at execution start (all 5 groups)   |
| `executing`   | Currently being applied to Discord                                          |
| `completed`   | All steps succeeded                                                         |
| `failed`      | One or more steps failed; rollback attempted                                |
| `rolled_back` | Rollback completed (after a failure or an after-the-fact rollback request)  |

### Status transitions

- `draft → validated`: execution starts and Stage 1 validation passes (a failed
  pre-execution conflict check or validation returns an error and the plan stays `draft`)
- `validated → executing`: guild lock acquired, mutations begin
- `executing → completed`: all steps succeed
- `executing → failed`: a step fails, rollback is attempted
- `failed → rolled_back`: rollback completes

### Staleness is tracked on the conversation, not the plan

`"stale"` is **not** a `PlanStatus`. When drift is detected, the code writes
`status: "stale"` to the **`conversations`** table (`plans.ts`), marking the
conversation view-only. Plans themselves are never marked stale — a plan built
from a now-stale conversation is simply never executed. Sibling conversations
whose `forkStateHash` no longer matches are the unit of staleness.

> Note: `approved` is a member of the `PlanStatus` type and is read in a couple
> of gate checks, but never written — approval is modelled at the conversation
> level. `rejected` does not exist in the codebase at all (not written, not read,
> not in the type).

## Storage tradeoffs

| Data                 | Location                                               | Rationale                                          |
| -------------------- | ------------------------------------------------------ | -------------------------------------------------- |
| Current DesiredState | `planData.desiredState` + latest `plan_iterations` row | Fast in-memory access; DB backup on server restart |
| Iteration history    | `plan_iterations` table                                | Versioned, queryable, bounded rows                 |
| Execution steps      | Generated on demand by diff engine; completed steps + symbol table persisted into `planData` after execution | Deterministic from DesiredState pre-execution; kept post-execution for audit |
| Server snapshots     | `snapshots` table                                      | Large blobs; separate table with expiration        |
| LLM conversation     | `conversations.messages` JSONB                         | Audit log; append-only                             |

02 — Discord foundations

Permissions are layered, not local.

ServerRoles are defined hereFor example: Admin, Moderator, Member, or Guest.
MembersReceive one or more rolesA member's access begins with the permissions granted by their server roles.
ChannelsCan override accessChannel permission overwrites refine access for a role or an individual member.

Channels do not own roles. They apply rules to server roles and members, which makes access deep and interdependent.

03 — The problem

Server administration is operational work disguised as clicking.

Repetitive setupRebuild the same structures for every community, team, or environment.
Costly mistakesOne permission error can expose channels or lock out the people who need them.
Difficult reviewIntent is scattered across messages, UI state, and undocumented decisions.
Repeatable configurationOrganisations need a reliable baseline.
Policy enforcementRules should be checked before they reach Discord.
Audit trailEvery meaningful change should be explainable.

The platform turns natural-language intent into a safe, reviewable configuration plan.

Why this matters04 / 15

04 — Failure mode

A structured AI response is still not a safe plan.

Ambiguous intent“Make support private” still needs exact roles, members, channels, and permission decisions.
JSON is not a contractValid-looking output can omit fields, reference the wrong resource, or conflict with live state.
No feedback loopA one-shot response cannot ask for clarification or update its plan after a failed assumption.

The solution: typed tool calls build DesiredState step by step, like a coding AI agent.

06 — DesiredState

Describe the target.
Not the clicks.

ImperativeDo A, then B, then CBlind API sequence. Fragile when the live server differs from expectation.
DeclarativeThis is the desired serverConfiguration is a stable target that can be compared, validated, and reapplied.

DesiredState is the shared language between user intent, AI planning, diffing, and execution.
